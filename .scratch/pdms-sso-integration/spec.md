# PDMS SSO integration alignment for Folio Forms

Status: ready-for-agent

## Problem Statement

PDMS Users need to open an ordinary Folio Form using their existing PDMS authentication without sharing passwords or login tokens between applications. Folio already implements the SSO Bridge, Legacy Identity mapping, account provisioning, Pending Account Link review, browser Session handoff, account switching, and Form re-entry. This effort changes that implemented integration to consume the agreed PDMS identity contract; it does not rebuild the SSO stack.

The current consumer requires `email_verified: true` and marks newly provisioned Users as email-verified. PDMS Auth stores an authenticated account email but has no mailbox-verification evidence or email provider. The accepted product decision trusts that authenticated assertion without claiming mailbox verification. The current parser must therefore accept the truthful PDMS response, while new Users must not acquire a false `emailVerified` flag.

There is also an identity-continuity defect: a historical Pending Account Link with status `linked` can reject a later login when the PDMS email changes, even though the provider and stable subject already identify the same Folio User. Completed links must remain stable. Incomplete reviews must not become an avenue for stale approval or email-only attachment.

## Solution

Keep Folio's existing public SSO routes, secure transaction and browser claim, normal one-hour Session, local login, Admin review, account controls, and Form ownership guarantees. Configure the existing bridge for PDMS Web Portal authorization and PDMS Auth exchange. Accept PDMS Auth's authenticated stable subject and valid stored email with `email_verified: false`, provision an ordinary enabled User without a local password when no collision exists, and use a valid optional PDMS display name only during initial provisioning.

Resolve completed identities by their configured provider and subject, not by a historical review email. If a pending or approved review's email changes, invalidate the stale review and require review of the current identity and correct candidate before a fresh SSO attempt can link them. Matching email alone never grants a Session or establishes a link.

Preserve the current browser experience: local and legacy login choices, clear pending and failure states, deliberate confirmation before switching to a different live Folio account, and save-before-reauthentication followed by return to the same User's Form Draft. PDMS and Folio credentials, Sessions, and logout remain separate. Prefill remains a separate email-bound handoff.

## User Stories

1. As an ordinary Folio User, I want the existing legacy login option to accept my authenticated PDMS account, so that I can open a Form without a second password.
2. As an authenticated PDMS User, I want my stored email to be trusted without a mailbox-verification requirement, so that the integration works without an unavailable email provider.
3. As an ordinary Folio User, I want PDMS login to avoid falsely marking my email as mailbox-verified, so that account assurance remains truthful.
4. As an ordinary Folio User, I want independently established local verification flags to remain unchanged, so that PDMS login does not erase or invent verification evidence.
5. As an authenticated PDMS User, I want my stable PDMS subject and configured provider to identify my Folio account, so that email changes cannot assign me another person's Responses.
6. As an ordinary Folio User, I want a completed Admin-approved link to survive a later PDMS email change, so that historical review data cannot block my established identity.
7. As an ordinary Folio User, I want later PDMS name and email changes not to overwrite my Folio profile, so that my local profile remains under Folio's existing controls.
8. As an authenticated PDMS User, I want a valid optional display name used when my Folio User is first created, so that my new profile can show my name rather than only my email.
9. As an authenticated PDMS User, I want an absent or invalid optional display name to use the existing email fallback, so that optional profile data does not prevent otherwise valid login.
10. As an authenticated PDMS User, I want an unused valid email to provision one enabled ordinary Folio User and one Legacy Identity atomically, so that I can begin filling without partial account records.
11. As an ordinary Folio User, I want automatic SSO provisioning to create no local password credential, so that the applications never copy or invent a shared password.
12. As an ordinary Folio User, I want concurrent first logins to converge on one account and identity binding, so that duplicate attempts cannot split ownership.
13. As an ordinary Folio User, I want failed exchange or failed persistence to grant no partial account, link, or Session, so that authentication failure cannot leave usable fragments.
14. As an ordinary Folio User, I want an email collision with an unlinked account to remain pending without granting access, so that another identity cannot acquire my Forms by email alone.
15. As an Admin, I want Pending Account Link review to show the authenticated PDMS identity and candidate Folio User without claiming mailbox verification, so that I can assess actual ownership evidence.
16. As an Admin, I want approval to require a genuine matching eligible Folio User, so that review cannot attach an identity to an Admin or disabled account.
17. As an ordinary Folio User, I want an email change during pending or approved review to invalidate the stale review, so that approval applies only to the identity and candidate actually reviewed.
18. As an Admin, I want changed incomplete reviews to require the current identity and correct candidate to be reviewed again, so that an old approval cannot silently authorize a new email relationship.
19. As an ordinary Folio User, I want approval to take effect only after a fresh SSO transaction, so that a code or callback issued before review cannot acquire my account.
20. As an ordinary Folio User, I want rejected and unapproved requests to remain unable to sign in, so that repeated attempts do not bypass an Admin's decision.
21. As an ordinary Folio User, I want PDMS roles not to grant Folio Admin access, so that Folio retains its independent authorization boundary.
22. As an ordinary Folio User, I want disabled-state and role checks to remain enforced at login, claim, and account switch, so that PDMS authentication cannot revive an ineligible Folio account.
23. As an ordinary Folio User, I want my browser's five-minute transaction, unpredictable state, and PKCE challenge preserved, so that another browser or callback cannot complete my login.
24. As an ordinary Folio User, I want expired, replayed, malformed, and mismatched callbacks rejected, so that a trusted email policy does not weaken callback security.
25. As an ordinary Folio User, I want Folio to exchange the exact opaque code through its authenticated server connection, so that browser credentials and code encoding do not corrupt or expose the handoff.
26. As an ordinary Folio User, I want a one-use browser claim within the existing 60-second window to deliver my normal opaque Folio bearer, so that the existing web app can authenticate without placing a Session credential in a URL.
27. As an ordinary Folio User, I want the existing current-account check to use my real Folio Session, so that browser profile text cannot impersonate the initiating account.
28. As an ordinary Folio User, I want same-account completion to preserve my intended Form, so that reauthentication does not move me to unrelated work.
29. As an ordinary Folio User, I want both identities shown before switching to a different live Folio account, so that I deliberately choose whose Forms I will use.
30. As an ordinary Folio User, I want cancel, failed exchange, or an expired switch challenge to preserve my current Session, so that a failed handoff does not replace my working account.
31. As an ordinary Folio User, I want switch confirmation bound to my current Session and displayed target, so that another browser or a changed target cannot reuse my consent.
32. As an ordinary Folio User, I want saved and unsaved Draft values never transferred to another account, so that switching identities cannot expose or corrupt another User's work.
33. As an ordinary Folio User, I want the existing one-hour Session warning to save my Draft before starting reauthentication while authorization remains valid, so that I can resume persisted work after login.
34. As an ordinary Folio User, I want a failed or unauthorized Draft save to stop the automatic reauthentication flow and show the failure, so that the interface never promises that unsaved work is safe.
35. As an ordinary Folio User, I want reauthentication to restore only my owned Response on the intended Form, so that a supplied response identifier never grants another User's Draft.
36. As an ordinary Folio User, I want only validated ordinary Form or dashboard return paths accepted, so that legacy login cannot redirect me to an attacker or mix in Prefill secrets.
37. As an ordinary Folio User, I want my local password login and temporary-password replacement requirement retained, so that SSO does not weaken local credential controls.
38. As an ordinary Folio User, I want server-established SSO provenance to bypass only an unused local temporary-password prompt, so that I can use SSO without clearing the local password-change requirement.
39. As an ordinary Folio User, I want Prefill login, email matching, code claim, cookie, and expiry requirements unchanged, so that direct Form SSO cannot bypass an email-bound Prefill Handoff.
40. As an ordinary Folio User, I want PDMS and Folio logout to remain independent, so that this integration does not imply synchronized revocation that it does not provide.
41. As an operator, I want environment-specific service endpoints, provider identity, and dedicated server credentials configured separately, so that deployments never rely on hardcoded secrets or URL credentials.
42. As an operator, I want an unavailable PDMS bridge to leave ordinary Folio local login usable, so that an optional integration does not become a second identity dependency for local accounts.
43. As an implementer, I want exact repository identities and ownership checked before application changes, so that missing or mismatched checkouts stop work instead of sending implementation to the wrong project.
44. As an implementer, I want accepted SSO documentation and behavioral tests to distinguish authenticated PDMS email from mailbox proof, so that implementation and published contracts describe the same assurance.
45. As an operator, I want controlled HTTP acceptance and actual browser smoke evidence separated from a live four-repository integration claim, so that release decisions rely on observed behavior.

## Implementation Decisions

- **Repository ownership and implementation gate.** `folio-forms` owns the consuming SSO transaction, identity resolution, provisioning and review, normal Folio Session handoff, account controls, and Form return. `pdms-auth-middileware` owns PDMS Auth identity authority and code issue/exchange. `pdms-web-portal` owns the existing login UI, same-origin authorization page, and safe login recovery. `pdms-ongoing-project-management` owns ordinary Form navigation and complete encoded login-return deep links; it does not implement another authorization page. Before application implementation, resolve all four required checkouts, confirm these exact names and roles, and STOP if any required checkout is missing or mismatched. Do not guess, clone, switch to, or silently substitute another repository.
- **Delta within current modules.** Modify the existing Elysia SSO exchange identity parser, provider trust policy, Legacy Identity resolution/provisioning, and Pending Account Link transitions. Reuse the existing PostgreSQL/Prisma User, Account, Session, Verification, and link-request persistence, Better Auth Session provenance, server environment validation, web API/authentication client, login and account-switch surfaces, Admin account-link review, and Form lifecycle. Update their existing contracts, fixtures, and acceptance tests where behavior changes. Do not create a parallel SSO module, alternative session system, or new client registry. Existing models already provide the required identity boundary; no new UUID identity field or mailbox-verification subsystem is required.
- **Retain exact Folio public routes.** Keep `POST /api/legacy-sso/start`, `GET /api/legacy-sso/callback`, `POST /api/legacy-sso/session`, `GET /api/legacy-sso/status`, `GET /api/legacy-sso/switch`, `POST /api/legacy-sso/switch/confirm`, and `POST /api/legacy-sso/switch/cancel`. Start continues to accept a JSON body containing only optional `returnTo` and returns `authorizationUrl`. This JSON start body is not the exchange transport. Keep Admin review at `GET /api/admin/account-links` and `POST /api/admin/account-links/:id/approve` or `/reject`. Do not introduce `/auth/legacy/*` aliases.
- **Shared browser contract.** Folio targets `GET /sso/folio/authorize` on PDMS Web Portal with `client_id`, exact `redirect_uri`, random `state`, `code_challenge`, and `code_challenge_method=S256`. Portal owns authenticated recovery, first using its existing refresh-cookie helper and requesting login only when necessary. Its same-origin authorization request must survive login recovery intact. Successful PDMS authentication hands off automatically; no new routine PDMS confirmation page is required. Folio's different-account confirmation remains required.
- **Shared issuer contract.** Portal calls bearer-authenticated `POST /api/sso/folio/issue` on PDMS Auth with `client_id`, `redirect_uri`, `state`, `code_challenge`, and `code_challenge_method=S256`. PDMS Auth validates the current non-deleted, unexpired account and valid stored email, then issues a cryptographically random, hashed, PostgreSQL-backed code bound to the account, dedicated client, exact callback, and S256 challenge. Code lifetime is 60 seconds. Portal navigates to the backend-built `redirect_url` containing `code` and unchanged `state`; it does not construct an arbitrary callback. This issuer is owned by `pdms-auth-middileware`, not reimplemented in Folio.
- **Exact exchange contract.** Folio makes a backend-to-backend `POST /api/sso/folio/exchange` using HTTP Basic authentication with the dedicated client ID and secret. The request is `application/x-www-form-urlencoded` with `grant_type=authorization_code`, `client_id`, `code`, `redirect_uri`, and `code_verifier`. The body client ID must match the authenticated client and code binding. Preserve exact opaque code form encoding, including `+`, `/`, and `=`, disabled exchange redirects, and the existing bounded five-second timeout. PDMS Auth rechecks the current eligible account and atomically consumes the valid, unexpired, client/callback/PKCE-bound code. Concurrent or replayed requests cannot produce a second success.
- **Truthful response and configured trust.** Exchange returns bounded JSON with `sub`, current valid stored `email`, optional `name`, and `email_verified: false`. `sub` is the decimal string representation of existing PDMS `users.id`; the issuer must not reassign it to another person, and deletion/recreation receives a new ID. The public field is `sub`, not `subject`. Do not accept a deprecated dual-field parser or JSON exchange shim. For the explicitly configured PDMS provider, accept authenticated PDMS email without requiring `email_verified === true`; consume the truthful false assertion rather than pretending it is mailbox proof. Do not broaden this trust to an arbitrary provider or caller-supplied issuer.
- **Preserve identity validation.** Keep response content-type and size limits, malformed-response rejection, nonempty bounded stable subject validation, valid bounded email validation and normalization, exchange authentication, and fail-closed errors. Missing or invalid subject/email does not create a User, link, or Session. Optional name does not replace either identity field. No PDMS password, access token, refresh token, role grant, or Folio Session credential belongs in the exchange response.
- **Initial provisioning only.** For an unlinked provider/subject with a free valid email, create one enabled `role=user` Folio User and its unique provider/account mapping transactionally. Set the new User's `emailVerified` to false; PDMS login is not mailbox evidence. Use an optional trimmed, nonblank, control-character-free display name within the existing 120-character account-name limit. If it is absent or invalid, retain the existing normalized-email name fallback. Create no `credential` account, password hash, shared password, or copied PDMS token. Preserve concurrent first-login convergence and rollback on failure.
- **No profile or assurance synchronization.** For an existing linked User, do not update name, email, `emailVerified`, local credential state, or `mustChangePassword` from PDMS claims. Preserve independently verified/local flags, including existing true values. Do not blanket-rewrite historical Users created by the earlier implementation; the new truthful provisioning policy does not establish which historical flags have independent evidence.
- **Stable completed link wins.** A completed Account mapping keyed by `(providerId, accountId)` identifies the Folio User, with `accountId` holding the stable PDMS subject. A historical status-`linked` review must not require its old email to match the current PDMS email, re-key the identity by email, rerun initial approval-generation checks, or override the completed mapping. Recheck the mapped User's current role and enabled state. Retain mapping conflict protection: a review is not authority to replace an Account mapped to another User.
- **Incomplete review remains fail-closed.** A pending or approved request is not a completed link. If its asserted email or candidate email changes before linking, its previous review cannot authorize login. Invalidate the stale approval and require review of current authenticated identity data against the correct eligible candidate. Do not silently reuse the old candidate, auto-attach by the new email, or escape unresolved review through automatic provisioning. If no matching eligible candidate can be established, keep login denied and do not allow approval of a mismatched candidate. Rejected requests remain denied under existing review rules. Resolve concurrent changes and review decisions transactionally so an old decision cannot become effective after the data changes.
- **Retain fresh-attempt safeguards.** Approval remains an Admin decision about a genuine matching ordinary User, not evidence of mailbox verification. Record the reviewed generation and require an SSO transaction generation strictly newer than the review before creating the link. A pre-review code/callback, wrong subject/provider, unapproved request, or concurrent stale callback grants no Session. Once the binding is completed, future logins use that binding rather than treating the completed request as an unfinished approval.
- **Independent authorization and ownership.** All SSO targets must remain enabled `role=user` Folio accounts. PDMS roles never grant Folio Admin. Preserve role/enabled checks through Session claim and switch as well as callback. Responses, Drafts, Submissions, storage access, and Operations continue to use Folio User ownership, never PDMS email or subject as an owner replacement. Changing PDMS email to another Folio User's email does not move an existing link or expose that User's data.
- **Retain browser transaction and transfer.** Keep the five-minute server-held transaction, random 43-character base64url state, S256 challenge, server-held RFC 7636 verifier within the existing 43–128-character validation bounds, Secure HttpOnly host-only pre-login cookie, exact callback validation, one-time transaction consumption, and server-side initiating Session capture through Folio's real authentication interface. Keep the 60-second Secure HttpOnly host-only browser transfer, existing SameSite behavior, and one-time `POST /api/legacy-sso/session` claim through the existing credentialed web request and exact configured Origin checks. The Folio API callback origin and `CORS_ORIGIN` web origin may differ; do not impose a new same-origin-only deployment constraint or wildcard Origin. Deliver the normal opaque Folio bearer in the HTTPS response body for the existing web client's storage and bearer authentication. A redirect alone is not completion. No bearer appears in a URL, and expired, replayed, foreign-origin, or browser-unbound claims remain denied.
- **Retain account switching.** The current authenticated Folio Session, not email text or guessed browser identity, identifies the initiating User. Preserve the owner-bound switch challenge, display of current and target identities, displayed-target confirmation binding, expiry and replay protection, and explicit confirmation before replacing a different live account. Same-account completion preserves the validated destination. Cancel or failure preserves the current account and Session. Never carry the old account's unsaved values or owned response identifier into the new account; confirmation must use the existing save/discard and owner-safe destination behavior. Revoked or changed initiating Sessions and ineligible targets remain blocked.
- **Keep local credential constraints separate.** Preserve server-controlled Session `isSso` provenance. SSO may bypass only the local temporary-password prompt for an otherwise eligible User; do not clear the stored password-change requirement or allow the browser to set provenance. Ordinary local password login still requires password replacement and retains existing revocation and authorization rules. Do not enable public self-registration or add a local credential for SSO-created Users as part of this work.
- **Keep one-hour Form lifecycle.** Better Auth continues to issue non-refreshing one-hour Folio Sessions. Keep the existing warning and save-before-reauthentication ordering, completing the Draft's document/data save and associated Operation while the existing authorization still permits it. Start SSO only after a successful save. A failed save, expired bearer, or unavailable persistence must show failure and stop the automatic path rather than pretend the Draft was saved. Same-user re-entry restores the owned Draft on the intended Form; a different authenticated identity cannot resume those values.
- **Separate four destination concepts.** Ordinary PDMS login return is Portal same-origin or the exact configured Ongoing origin, with complete path/query preserved and arbitrary origins/unsafe schemes rejected. This is not the SSO callback allowlist. PDMS authorization is the configured Portal `/sso/folio/authorize` URI. The registered callback is the exact public Folio API `/api/legacy-sso/callback` URI. Folio success/failure browser redirects use the trusted Folio web origin from `CORS_ORIGIN`, never request Host, forwarded headers, or caller input. Existing direct K2/sidebar links are not new login-return allowlist entries.
- **Retain Folio return validation.** Folio's SSO `returnTo` is an existing local `/forms/<32-character lowercase hexadecimal publicId>/fill` path, optionally with one valid UUID `responseId`, or `/dashboard` without a query. Reject external/protocol-relative destinations, unsafe encodings, backslashes, control characters, fragments, duplicate/unknown query fields, and Prefill material. A syntactically valid response identifier still requires owner authorization; validation never grants data access.
- **Configuration is the service contract.** Configure Folio's existing six server keys together per environment: `LEGACY_SSO_AUTHORIZE_URL`, `LEGACY_SSO_EXCHANGE_URL`, `LEGACY_SSO_CALLBACK_URL`, `LEGACY_SSO_CLIENT_ID`, `LEGACY_SSO_CLIENT_SECRET`, and stable `LEGACY_SSO_PROVIDER_ID`. Keep the existing provider ID for established PDMS links; do not rename its mapping namespace as a branding change. Keep `CORS_ORIGIN` as the trusted Folio web redirect origin and existing authentication/API-origin configuration separate. PDMS Auth owns `FOLIO_SSO_ENABLED`, `FOLIO_SSO_CLIENT_ID`, `FOLIO_SSO_CLIENT_SECRET`, and `FOLIO_SSO_REDIRECT_URI`; IDs, dedicated secrets, and exact callbacks must agree with Folio. The dedicated secret is not `X_PDMS_AUTH_SECRET`. Frontends reuse their public Auth/Portal/Ongoing configuration and receive no service secret. Never hardcode secrets, endpoint credentials, or personal email-provider credentials. Keep all-unset Folio SSO configuration disabled, retain existing fail-fast partial/invalid configuration handling, and preserve local login when the optional bridge is disabled or unavailable. Do not add a browser CORS permission solely for server-side exchange.
- **Transport and confidentiality remain unchanged.** Use HTTPS outside explicitly configured loopback development. Endpoints reject URL credentials and unsafe endpoint forms. Authorization responses are non-cacheable. Never log raw codes, client secrets, tokens, PKCE verifiers, or full callback/redirect URLs. Neither application borrows the other's access/refresh tokens or Session credentials. No mailbox-verification service or provider is introduced.
- **Amend the accepted decision during implementation, not specification publication.** Explicitly amend only the conflicting verified-email clauses of accepted legacy SSO ADR 0002 and their associated API documentation, fixtures, assertions, and glossary descriptions. Describe an authenticated PDMS Legacy Identity and Admin-reviewed ownership without asserting mailbox proof; document optional initial name and stable completed-link behavior accurately. Remove the obsolete provider-email equality prerequisite for a fully linked identity. All other ADR guarantees, route contracts, local authorization, Pending Account Link review, account switching, and separate Prefill behavior remain in force. Do not reopen the completed baseline expansion tickets.

## Testing Decisions

- Extend the existing highest Elysia HTTP application acceptance seam rather than introducing another harness. Existing SSO journeys use real Better Auth, Prisma/PostgreSQL, private document storage, Folio ownership checks, and a controllable old-backend HTTP contract service. Controlled counterpart behavior is contract evidence, not a claim that all four production services were exercised.
- Test public HTTP outcomes and durable account/link/Session transitions. Do not assert private helper names, source text, copied wiring, mock echoes, arbitrary wording, or bare absence of exceptions. Fixtures must be isolated and full-suite-safe. Existing tests that demand rejection solely because `email_verified` is false or that assert false mailbox assurance must change with the new semantic contract, not be re-pinned to obsolete behavior.
- Prove a truthful PDMS response with `sub`, valid email, optional name, and `email_verified: false` can complete initial and linked SSO. Prove missing/invalid subject or email, malformed/oversized/non-JSON exchange bodies, failed authentication/exchange, and disallowed exchange redirects still grant no login. Exercise exact form encoding of an opaque code and authenticated redemption as an externally observable protocol outcome, not by inspecting source or forwarding mocks.
- Prove first provisioning yields one enabled ordinary User, one provider/subject mapping, no password credential, false `emailVerified`, and the valid initial name. Prove absent, blank, over-limit, or unsafe optional names use the email fallback without profile injection. Prove later PDMS names/emails do not overwrite linked profile or independently established flags. Include concurrent first login and persistence rollback outcomes.
- Reproduce the historical status-`linked` request defect before changing resolution. After the change, authenticate the same provider/subject with a new valid PDMS email, including an email used by a different Folio User, and prove it resolves only the originally linked User, preserves that profile, and cannot read the other User's Responses. Do not require provider email to equal the linked Folio profile email.
- Test pending and approved email changes separately from completed links. A stale approval or candidate mismatch must not create a binding or Session. Prove the current identity and correct eligible candidate require fresh review and a newer transaction after approval. Retain rejection, wrong-provider/subject, Admin/disabled candidate, pre-review callback, generation boundary, concurrent review/change, and concurrent stale-callback regressions. Prove email alone never attaches an account.
- Retain five-minute transaction and 60-second claim boundary tests, browser-cookie/state/PKCE binding, exact callback checks, replay/concurrent consumption, foreign-origin claim denial, trusted web redirect origin, and no Session credentials in redirect URLs. Keep non-cacheable failure/pending/success responses and local login when SSO is unavailable.
- Retain current-account capture, same-account Form return, different-account identity display, explicit owner-bound switch confirmation, cancellation, stale target, revoked initiating Session, disabled target, and switch expiry/replay outcomes. Assert that cancel/failure leaves the current bearer usable and that confirmed switches cannot resume the previous User's Draft or apply unsaved values to the target account.
- Retain local password login and password-change enforcement, server-established SSO provenance, unchanged stored temporary-password requirement, one-hour Session expiry, and independent PDMS/Folio logout behavior. Do not assert immediate cross-system revocation that the contract explicitly excludes.
- Reuse the focused web Form lifecycle safe-return and save-order tests. Prove reauthentication waits for successful document/data persistence, save failure stops navigation, expiry does not authorize a save, and same-user re-entry restores the persisted owned Draft. Keep a public HTTP ownership scenario with real Draft storage and Operations; test completion and resumed values, not only calls or event forwarding.
- Retain Form return rejection and separate Prefill regressions: arbitrary/unsafe destinations, forbidden query material, invalid or foreign-owned `responseId`, and unchanged Prefill email match, code claim, cookies, and expiry. No SSO shortcut may satisfy a Prefill requirement.
- After implementation, smoke the actual browser surfaces: Folio legacy login through Portal authorization and expired-login recovery; callback and normal bearer claim; initial profile display; Pending Account Link and Admin review followed by a fresh attempt; completed-link login after PDMS email change; account-switch confirm/cancel; and Form save-before-reauthentication with owner-safe return. Observe the resulting account, usable Form, saved Draft, and failure/pending controls. Existing UI and browser tooling are the seam; no new framework is requested.
- Report controlled HTTP results, focused lifecycle results, and browser observations separately. Full deployed end-to-end acceptance additionally requires all four implementations and matched per-environment configuration. Specification writing itself runs no tests, application servers, or browser smoke.

## Out of Scope

Rebuilding the completed Folio SSO stack; a second authorization page in Ongoing; generalized OAuth/OIDC identity-provider or client registration; mailbox verification, email delivery, an email-provider dependency, or personal provider credentials; fabricated `email_verified: true`; password/token sharing; email-only linking or automatic account merging; linked-profile synchronization; bulk historical verification-flag rewrites; PDMS-derived Folio Admin grants; synchronized logout or immediate Folio revocation after a PDMS account change; public self-registration; a new PDMS identity identifier; unrelated PDMS account-uniqueness changes; weakening local temporary-password controls; merging Prefill with SSO; broad AI authoring, native-fill, results, editor, or static-server work; reopening completed Folio expansion tickets; application implementation, test execution, and ADR/glossary edits during this specification publication; remote issue publication.
